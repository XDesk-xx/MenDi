# Design

## Context

动机见 proposal。017 的真实 CLI Explore start / instructions 和四阶段 loader 读取，加上 018 的动态 context 与 Reviewer 不继承 Author 上游的对抗复验，支持沿用现有方法传递；它们不证明宿主已能作出正确语义判断。

当前 `loadChangeMethods` 从安装根读取阶段方法、从目标读取必要官方方法；角色、optional guidance 和普通查询边界已成立。自有方法已规定阶段与证据，但缺少本次业务 / UI 尺度。现有 `action-runs` 和 `storybook-integration` 可承载合同，不新增近义能力或数据格式。

## Goals / Non-Goals

**Goals:** 让各角色在其实际取得的短方法中读到本阶段职责；以明确业务后果判断 UI 和产品未知；保持普通 UI 不新建 Change、Reviewer 独立、旧记录不改。

**Non-Goals:** 自动识别 UI 等价、解析 Owner 对话、模型评分器、问答注册表、自动改写历史规格、通用 UI 工程或浏览器矩阵；不调整 CLI、上游官方方法、稳定安装、版本与发布接线。

## Decisions

### 1. 在自有阶段正文承载判断，不改 loader

| 落点 | 本阶段最小职责 |
| --- | --- |
| explore | 查事实和既有决定，区分业务约束 / 候选 UI / 关键未知，按依赖提问与必要 proof |
| propose | 定稿前复核答案，安排 specs / design / tasks；普通 UI 不新建 Change，不把重要假设留给 Apply |
| review-explore | 核对区分、proof 适用性和提问必要性，不凭工具成功批准 |
| review-propose | 核对业务与 UI 粒度、未确认假设和答案承接，用同尺度判断用户影响 |
| apply / review-apply | 保留已批准合同与原场景，按真实入口修复定位并验证 / 独立核对，不以弱化用例取得通过 |

保持方法名称、phase、role 和既有阶段入口不变；revise / continue 继续使用已有对应方法。Reviewer 本身需要读到简短判断义务，不能只引用它不必加载的 Author 上游。也不新建跨阶段必读文件或把长文复制到六处：共同原则作少量必要重述，各阶段只讲实际责任。

备选：改目标 context 或上游适配。这会将产品通用方法混入目标背景、重复维护或改变来源，当前交接未见技术缺口，故不采用。若 Apply 真出现必要接线缺口，先说明实际影响再收敛受审范围，不默默扩建。

### 2. 先判断用户影响，不按 UI 名词机械分类

普通菜单、文案、布局、页面组织和滚动交互可正常更新设计 / 测试，不为它们新建 Change，也不新增 Action / Run 手续。旧规格提到“顶部菜单”不自动使位置成为业务承诺；既有词面与当前 UI 不同，先核对实际目的、对象、可达性和已确认要求。

“保存草稿”改“发布”即使 handler 相同，也可能影响用户预期；Owner 明确作为验收的入口要求不能被模型降格。默认提交值、权限、确认、历史或不可逆后果改变且决定未知时，向 Owner 问具体影响，按既有流程处理，不自动将所有差异归为必须新 Change，也不靠 design 备注豁免真正承诺。本次不发明新的规格豁免机制。

备选：旧 UI 文字一律强制新 Change，或一律当 design。前者违背 Owner 已确认决定，后者可能放松业务边界，均不采用。

### 3. 澄清是实际阶段工作，不建机器门禁

先查可直接核实的代码 / 配置 / 文档和已确认回答；仅对会改变产品或验收的关键未知提具体问题，说明答案影响，有依据时给建议。按问题依赖顺序推进，答案未到只暂停依赖部分；低影响可逆细节自行判断并简记。

用当前 Run 和正式产物承接必要决定 / 未决 / 限制；没有新字段、统一问答模板、审批层或默认等待时长。Review 检查重要假设是否被冒充为确认，不靠“有问句 / 回答数量”自动判定。非 UI 的数据保留或兼容未知同样适用。

### 4. 把传递实测与语义验收分开

Apply 沿用现有 TypeScript 测试与夹具机制，核对六阶段自有正文及修订映射、Author 目标上游来源、Reviewer 无 Author 上游前置、未选 Storybook 不加载指导。至少一个真实候选 CLI 交接及真实 instructions 核对更新后的实际正文 / context；不为取六份正文伪造完整阶段批准。

复用已有 `tests/target-methods.test.ts`、`tests/target-method-handoff.test.ts` 和 `tests/methods-and-numbers.test.ts`，核对返回正文等于真实来源、角色 / 方法身份及选择关系；仅在发现实际交接覆盖缺口时补充相应场景，不为方法文本重复添加关键词测试或镜像断言，不扩展旧 Explore proof 成整轮验收。

实际语义由 Author 在当次 Apply Run 以具体输入、事实 / 未知、处理与理由说明，Reviewer独立核对；不把人工推演称为 UI 运行 PASS。代表边界如下，覆盖不以固定数量作为产品 gate：

| 代表输入 | 应区分的后果 |
| --- | --- |
| 顶部菜单改侧栏，能力 / 对象不变 | 普通 UI 不新建 Change；旧名称不机械冻结设计 |
| 合并页面后历史入口丢失，直达仍成功 | 正常可达性缺口，不能凭接口 / URL 豁免 |
| 分页改滚动但键盘不可达，或存在 PDF 逐页要求 | 关注实际功能 / 可用性，不能按设计标签一概放行 |
| “草稿”改“发布”，Owner又明确要求某确认文案 | 判断理解及明确验收承诺，不只看 handler |
| 默认截止 / 时区 / 请求值未决 | 先问产品行为，不能将模型默认写成规格 |
| 非 UI 数据保留未答、等待一段时间 | 暂停依赖定稿，等待不等于批准 |
| 权限泄漏 / 未确认提交，测试仍绿 | 业务缺口不能由工程结果豁免 |
| 旧定位失效，force / 删断言后绿 | 保留场景、必要技术断言、失败和清理，用真实当前入口 |

本 C 不实现这些 UI，也不另造完整目标生命周期；真正目标后续采用新方法时，按其变化取得实际 UI 测试 / 浏览器结果。语义案例不能认证任意宿主会遵循指令。

## Risks / Trade-offs

- 方法短但遗漏关键边界 → 用代表情形核对，并让 Reviewer 独立看实际正文，而非按关键词评分。
- “UI 不开 Change”被误读为无条件豁免 → 同时写清实际业务影响、必要可达性和明确验收约束；不增加自动新 Change 规则。
- 作者与审核依赖不同方法 → 两方各自正文具备本阶段必要尺度，不强加 Author 上游给 Reviewer。
- 交接测试绿被当成语义认证 → 分别记录传递实测与人工语义核对，保留限制。

## Migration Plan

只面向后续方法使用；既有归档、submitted Run、verdict 和当前产品格式不迁移、不回填。当前源码 Skills 经获准 Apply、独立 Review Apply及授权归档后，随将来获准版本包发布；本 Change 不切换稳定安装或其他项目。

Apply 运行 `pnpm check`、受影响方法测试及必要真实交接。未改变运行时代码 / 记录合同，不预设重跑全部根测试、旧 UI 工程或完整 Explore 树；若实际扩大影响，在当次 Run 说明并增加相应验证。后续正式 Delivery Full Test / Close、版本准备、Git、安装和 DreMo 推进另依授权。

# Proposal

## Why

现行 Full Test 只保存整条命令结果：目标入口中段失败可能跳过独立后项，修复审核后又必须重跑原完整集合。009 Explore 和最新 011 独立对抗实验进一步证明，pass 事件、成功文件集合、包装器退出 0 和 collection 文本都不能单独证明必需范围已经完成。需要让目标明确报告组级事实，保留每次真实失败，同时形成可供 Close 核对的当前候选结论。

## What Changes

- 增加可选 `mendi-group-tests/1` 协议：目标提供有序逻辑组、少量必要依赖、资源边界、完成条件及最终回执；MenDi 固定本次计划、选择与身份，并消费实际结果。目标继续负责测试拆分、实际业务执行、构建、端口、数据和清理，不增加通用调度平台或前端。
- 旧入口默认保持 `command` 模式，已有普通 / 正式单次结果继续按原合同读取。结构化模式显式接入，不能从 stdout、文件名、旧 command PASS 或 collection 文字推导组事实。
- 必需测试组须实际执行其未排除的业务范围；skip / TODO、取消、零执行或未完成均留下缺口。非必需项只能在执行前计划中明确排除并说明理由。混合成功失败、晚退出、未确认清理、包装器 / 回执矛盾和终态保存失败不能被早期 pass 或另一通道的成功覆盖。
- 以新的 `delivery-test-attempt` 记录保存结构化首次执行、同轮续测及复验，保留原始命令 outcome 与协议观察。独立失败继续可执行后项，依赖失败仅阻断相关项；全局取消停止整轮，资源未知阻断共享后项，影响无法界定时停止相关执行。
- 以独立 `delivery-verification` 记录保存当前候选完整结论，列出每个必需组的直接来源、适用性、必要修复批准和缺口；不改写尝试，不把多个来源伪称为一次命令成功。不另增汇总 Reviewer 阶段。
- **BREAKING（仅显式新模式）**：新记录类型、协议版本与 Close 的 `verificationRunRef` 选择不能由旧消费者忽略后当作旧 Full Test。未知版本 / 类型明确拒绝；旧 `fullTestRunRef` 单次分支保持，旧数据不批量补字段、不追溯生成组事实。
- 将 Full Test 查询、repair / review、status / next 和 Close 接到相同的当前轮候选事实。材料以提交及必要差异或明确说明指认，Author 逐组说明影响，独立 Review 核对；工具检查来源、覆盖、批准及一致性，不自动认证任意源码或建立全库 hash。
- 增加有包含关系的单调阶段计时、UTC 追溯和增量进度；提供受控 Node 参考接线及短场景，测量真实热点。在同次目标执行内核对只读准备复用和有限并发的前提，不承诺提速比例、不扩大到 DreMo 优化或放宽业务预算。

## Capabilities

### New Capabilities

无；在已有执行、正式验收和生命周期能力内扩展。

### Modified Capabilities

- `test-execution`：可选计划 / 请求 / 回执、组完成与退出一致性、依赖及资源阻断、取消、阶段时间和必要直接读取。
- `delivery-verification`：结构化尝试、同轮续测、修复后的按影响复验、当前候选验证结论、旧单次兼容及统一查询交接。
- `delivery-lifecycle`：Close 显式区分旧单次结果与新候选结论，保存当前轮直接验收快照，拒绝覆盖缺口、来源矛盾和未确认状态。

## Impact

涉及 core 的执行 / 正式结果与候选解释、adapters 的协议文件 / 结果持久化、application 的 Full Test / repair / 查询 / Close，以及 CLI 和随包方法。实施前继续分离实际准入、执行与解释职责，尤其不能把新协议、全部聚合和兼容分支堆进现有项目入口。

新协议的计划和输出均在当前项目受管路径内，沿现有锁、编号和真实前台进程树边界执行；不自动安装、不抢端口、不自动清锁或恢复未知执行。根 manual-bootstrap、A 的 011 归档、旧 Run / verdict / 日志、路线图及三份反馈原件保持。

本 Change 将执行和正式消费一起交付。Apply 需覆盖 011 的 E1–E6 反例及完整续测 / 修复 / 汇总 / Close 链，进行必要工程及回归检查；本 Propose 不实现产品，不执行真实目标迁移、DreMo 修改、稳定安装切换、Git、根正式 Full Test / Close 或 C 激活。
